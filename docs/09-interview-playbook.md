# 面试 Playbook：把这个仓库讲成一个故事

> 这份文档不是知识清单，是**话术与结构**。技术细节在其余文档里，这里解决的是
> 「怎么在 30 分钟内让面试官相信你真的做过」。

---

## 一、开场：三分钟版本

面试官说「介绍一下你这个项目」。**不要从技术栈开始讲**，那会立刻变成背书。

按「问题 → 约束 → 选择 → 证据」四步走：

> 我搭了一个订单服务的完整交付链路，从代码提交一直到生产环境的金丝雀发布和自动回滚。
>
> 起因是我发现自己在做量化系统时，**部署这件事一直是黑盒**——代码写完推上去，
> 后面发生了什么我不清楚。所以我想把它拆开，每一环都自己搭一遍。
>
> 我给自己定了三条约束：**第一**，不能只写配置，必须真跑通，所以 CI/CD 都挂在
> 真实的 GitHub Actions 上，你能看到执行记录；**第二**，环境要能复现，
> 集成测试用 Testcontainers 起真实 PostgreSQL，不依赖我本地装了什么；
> **第三**，每个决策都要能说出「不这么做会怎样」，因为配置谁都能抄，
> 但出了问题能不能定位是另一回事。
>
> 最后交付的是：CI 全绿、一次成功的金丝雀发布、以及一次**故障注入触发的自动回滚**——
> 回滚那条 run 里能看到 AnalysisRun 判定失败和 Rollout 中止的完整日志。

**关键点**：把「我做了 X」换成「我遇到了什么问题，所以我选择 X」。
前者是简历，后者是经历。

## 二、十分钟版本：按链路走一遍

面试官追问「详细说说」。按下面的顺序讲，每段控制在一分钟：

### 1. 代码组织（1 分钟）

> 四个 Maven 模块，依赖方向严格单向：api → core → common，
> 第四个模块只做一件事——把各模块的覆盖率数据合并成一份跨模块报告。
>
> 有两个结构决策踩过坑。**集成测试我放在 api 模块而不是 core**，
> 因为 `@SpringBootTest` 需要启动类，启动类在 api，放 core 会造成循环依赖。
> **JPA 配置我也从启动类挪到了 core 模块**——写在启动类上的
> `@EnableJpaRepositories` 会跟着 `@WebMvcTest` 切片一起加载，
> 而 Web 切片里没有 JPA 自动配置，结果所有控制器测试都因为
> 「找不到 entityManagerFactory」失败。报错完全指向 JPA，
> 跟控制器没关系，排查方向被带偏了很久。

**这里展示的是**：你理解测试切片的加载机制，而不是会写 `@WebMvcTest` 注解。

### 2. 测试分层（1.5 分钟）

> 三层：纯单测用 Mockito，毫秒级；`@WebMvcTest` 切片测 HTTP 契约，
> 只加载 Web 层；`@SpringBootTest` + Testcontainers 做端到端。
>
> **集成测试我坚持用真实 PostgreSQL 而不是 H2。** H2 的 SQL 方言、
> 约束语义、事务隔离都和 PG 不同，用它测出来的「通过」不能说明生产能跑。
> 代价是每个测试类要等容器启动，本机 2-4 秒。我认为这个代价值得，
> 因为「集成测试通过 = 生产也能跑」这个结论必须成立。
>
> 覆盖率门禁我没用现成的 action，自己写了个脚本解析聚合报告。
> 原因是第三方 action 在不同事件类型下行为不一致，
> 而**门禁最忌讳的就是「有时候不生效」**。脚本卡三道：
> 全局行覆盖率 80%、分支 70%、单个模块不低于 60%——
> 最后一道是为了防止一个高覆盖率的模块掩盖另一个零覆盖的模块。

### 3. 容器化（1.5 分钟）

> 多阶段构建。builder 阶段用 Maven 镜像编译，runtime 阶段只带 JRE。
>
> 有几个点值得说。**builder 阶段必须把所有子模块的 pom 都 COPY 进去**，
> 只 COPY 根 pom 会直接构建失败——Maven 读到 `<modules>` 但子目录不存在，
> 依赖缓存那一步就中断了。
>
> **ENTRYPOINT 必须用 exec 形式**。用 shell 形式会包一层 `/bin/sh -c`，
> java 进程就不是 PID 1，收不到 k8s 发的 SIGTERM，优雅停机完全失效，
> 滚动更新时会出现 502。
>
> 还有一个取舍：**多阶段自包含构建的代价是每次 CI 都要重新下载 Maven 依赖**。
> 因为 BuildKit 的 cache mount 不在镜像层里，GHA 的层缓存覆盖不到它。
> 如果追求 CI 速度，应该改成「CI 里先 `mvn package`，Dockerfile 只做组装」。
> 我选前者是因为它保证了「构建环境可复现」——不依赖构建者本机的任何东西。

### 4. 流水线（2 分钟）

> 五个 job。build-test 跑 `mvn verify`（含 Testcontainers 集成测试），
> 然后覆盖率门禁；依赖扫描用 Trivy 扫 pom 解析出的传递依赖；
> 清单校验用 kubeconform 加一个我自己写的跨资源引用检查；
> 最后构建镜像推 GHCR，再扫一遍镜像。
>
> 几个设计点。**权限模型**：顶层只给 `contents: read`，各 job 按需提权。
> 因为一旦某个第三方 action 被投毒，它能拿到的就是这个 job 的权限。
>
> **覆盖率门禁单独一步**，不塞进 `mvn verify`。这样失败时在页面上能一眼看出
> 是「测试挂了」还是「覆盖率不达标」——前者要修代码，后者通常要补测试，
> 处理方式完全不同。
>
> **Trivy 我用 `format: table` 加 `exit-code`，没用 SARIF。**
> SARIF 需要 GitHub Advanced Security，私有仓库要额外付费。
> 更重要的一个参数是 `ignore-unfixed: true`——只对「已有修复版本」的漏洞失败。
> 不过滤的话，一个还没发布补丁的 CVE 会永久卡住流水线，
> 团队最后只能选择关闭扫描。**门禁设计必须考虑「它会不会被绕过」。**

### 5. K8s 与金丝雀（2 分钟）

> 清单用 Kustomize，base 加 dev/prod/ci 三个 overlay。
>
> 探针这里有个容易搞错的点：**liveness 绝对不能包含数据库检查**。
> 数据库抖几分钟，所有 Pod 会被判定为不健康并集体重启，
> 把一次数据库故障放大成全站故障。所以 liveness 只放 `livenessState`，
> readiness 才包含 `db`。
>
> 金丝雀用 Argo Rollouts。**这里我要说明一个局限**：我没配 trafficRouting，
> 所以 `setWeight` 是按副本数近似的，不是真正的百分比分流。
> 生产环境要精确控流必须接 Istio 或 Nginx Ingress。
>
> **金丝雀分析我最后改成了 Job 探测，不用 Prometheus。** 原因是：
> 演示集群里金丝雀期间没有真实流量，错误率的分母是 0，
> PromQL 返回空集，AnalysisRun 会判 `Inconclusive`——
> 而 Inconclusive 不算失败，它会一直重试到 `progressDeadlineSeconds` 超时。
> **表面看是「回滚了」，实际是超时了。** 这两者的故障定位路径完全不同，
> 讲混了会显得没真跑过。Job 探测的退出码就是判定结果，秒级、确定、日志可读。

### 6. 可观测性（1 分钟）

> 自定义了三个业务指标。**这里踩了一个我认为最有价值的坑**：
> 我给计数器起名 `order.created`，以为抓出来是 `order_created_total`，
> 结果拿到的是 `order_total`——`created` 整个消失了。
>
> 原因是 **`_created` 是 Prometheus 文本暴露格式的保留后缀**。
> `foo_created` 表示「计数器 foo 的创建时间戳」，是 `foo_total` 的附属元数据。
> 所以 `order_created` 被解析成了「计数器 order 的 created 元数据」。
>
> 危险的地方在于**故障是完全静默的**：Grafana 查询返回空集而不是报错，
> 面板显示「无数据」，告警规则永不触发。我最后改成 `order.create`，
> 并且写了一个测试把命名映射固定下来。

## 三、高频追问与答法

### Q：CI 和 CD 的边界在哪？

> 我的划分是：**CI 回答「这个变更能不能上」，CD 回答「怎么安全地上去」。**
>
> 具体到 job：CI 包含构建、测试、扫描、产出镜像——全部是自动判定，
> 不需要人。CD 包含部署、放量、验证、回滚——涉及环境状态变更，
> 需要审批和可观测的决策点。
>
> 一个实际影响：CI 失败就是失败，重跑即可；CD 失败要考虑集群停在了什么状态，
> 所以我给 CD 配了 `cancel-in-progress: false`——部署不能被打断，
> 否则会停在中间状态。

### Q：覆盖率门禁定多少合理？

> 这个问题没有标准答案，但**有错误答案**：直接抄一个 80% 或者 90%。
>
> 我的做法是分三层：全局 80%、分支 70%、**单模块不低于 60%**。
> 最后一道最重要，因为只看全局会被平均掉——一个 100% 覆盖的模块
> 可以完全掩盖另一个 0% 覆盖的模块。
>
> 另外我**没有在模块级用 `jacoco:check`**。它只读本模块的 `jacoco.exec`，
> 没有聚合能力。绑上去之后，`demo-common` 这种纯 DTO 模块永远达不到阈值，
> 构建必然红。判定必须在读聚合报告的层面做。

### Q：滚动更新时为什么会出现 502？

这是高频题，答全四点：

> 四个原因，按出现频率排：
>
> **第一，`preStop` 缺失。** Pod 被删除时，k8s 是**并行**做两件事：
> 从 Endpoints 摘除，和发送 SIGTERM。而 kube-proxy 刷新 iptables 规则需要时间。
> 这个窗口里流量仍会转发到正在关闭的 Pod。加 `preStop: sleep 10` 等传播完成。
>
> **第二，`terminationGracePeriodSeconds` 小于应用的优雅停机超时。**
> 应用还在处理在途请求，k8s 已经发 SIGKILL 了。
>
> **第三，readiness 探针配得太松。** 应用还没真正就绪就被加进 Endpoints。
>
> **第四，ENTRYPOINT 用了 shell 形式。** java 不是 PID 1，收不到 SIGTERM，
> 优雅停机代码根本不会执行。

### Q：金丝雀的判定指标怎么选？

> 我的原则是**至少三类，缺一不可**：
>
> **错误率**——最直接，但单独用会漏掉一种情况：新版本因为配置错误
> 完全不接流量，此时错误率是 0，看起来完美。
> 所以要加**延迟分位数**和**正向流量指标**。
> 我那份 Prometheus 模板里第三条 `traffic-present` 就是防这个的——
> 「没有错误」和「没有流量」必须能区分开。
>
> 还有一个容易忽略的点：**判定窗口必须长于 `rate()` 的窗口**。
> 我用 `rate(...[2m])`，那分析至少要跑 2 分钟才有稳定值，
> 否则会取到不满窗口的数据，判定抖动。

### Q：回滚是回滚镜像还是回滚配置？

> 取决于**变更的来源**，而且这两者经常纠缠在一起。
>
> 镜像回滚相对干净：Argo Rollouts 把 stableService 的 selector 指回旧 ReplicaSet，
> 秒级完成，因为金丝雀期间 stable 的副本数一直保持满编，中止只需把 selector 切回去。
> （这里有个细节：没配 `trafficRouting` 时 Argo 不允许显式设 `scaleDownDelaySeconds`，
> 所以面试时要讲清「快」来自副本策略，而不是来自某个延迟缩容参数。）
>
> 配置回滚要危险得多。如果配置在 ConfigMap 里，而 ConfigMap 是
> stable 和 canary **共享**的——改它会把正在服务的稳定版一起打挂。
> 我在演示里刻意避开了这个陷阱：故障注入走的是 Pod 模板里的环境变量，
> 只影响新 ReplicaSet，stable 版本不受影响。
>
> 最麻烦的是**数据库变更回滚**。Flyway 社区版没有 `undo`，
> 所以只能靠 expand/contract 模式让新旧版本能同时运行。

### Q：数据库变更怎么做零停机？

这是区分度很高的一题：

> 核心原则是**任何一次发布，数据库都必须同时兼容新旧两个版本的应用代码**。
> 具体用 expand/contract 四步：
>
> **第一步 expand**：只加列，加可空列或者带默认值，不动任何现有列。
> 这一步对旧版本代码完全无影响。
>
> **第二步 双写**：新版本代码同时写新旧两处，读还是读旧的。
> 此时新旧版本可以共存。
>
> **第三步 回填**：后台任务把历史数据补齐。注意要限速，
> 全表 UPDATE 会锁表。
>
> **第四步 contract**：确认所有实例都是新版本、且观察期过后，
> 再删除旧列。**这一步必须单独发一次，不能和前面合并。**
>
> 关键认识是：**数据库变更不是「一次发布」而是一个跨越多次发布的周期**。
> 想在一个 release 里做完，就必然要停机。

### Q：Secret 怎么管？

> 我在仓库里放的是**占位模板加说明，不是可用的方案**。
> 因为把明文密码提交进 Git 是最常见的供应链事故来源——
> 一旦提交，即使后来删除，它也已经留在 Git 历史、CI 日志、
> 以及所有克隆过仓库的机器上，只能靠轮换密钥补救。
>
> 生产有四条路：**External Secrets Operator**（从 Vault/KMS 拉取，
> 密钥不落 Git，多集群场景最合适）、**Sealed Secrets**（集群公钥加密后提交密文）、
> **SOPS**（Git 里存加密文件，好处是能对单字段做 diff）、
> **云厂商的 CSI Driver**（密钥以文件挂载，完全不经过 etcd）。
>
> 我倾向 External Secrets，因为密钥轮换的责任可以交给后端系统统一管理，
> 而不是散落在各个仓库的加密文件里。

### Q：你怎么知道线上跑的是哪个 commit？

> 三处证据。**第一**，`git-commit-id-maven-plugin` 把 commit sha、分支、
> 构建时间注入 `/actuator/info`，直接 curl 就能看到。
> **第二**，镜像按 digest 部署而不是 tag——tag 是可变的，
> 同一个 tag 在不同时间可能指向不同内容，digest 是内容的 SHA256，不可变。
> **第三**，构建时生成 provenance 和 SBOM，记录这个镜像
> 「用哪个 Dockerfile、从哪个 commit、在哪个构建器上」产出的。
>
> 在受监管行业这不是加分项，是硬性要求——
> 审计问「三个月前上线的是哪份代码」，必须能给出确定答案。

### Q：扫描出高危漏洞怎么办？

这题能直接区分「配了扫描」和「会处置漏洞」：

> 我的原则是**先分两类：当前版本内能修的、不能修的**。
>
> 能修的就修。我实际处理过四类：基础镜像的 `libexpat` 用 `apk upgrade` 补；
> Jackson 的 4 个 DoS 通过覆盖 `jackson-bom`（注意必须放在 Boot BOM **之前**，
> 先声明者优先）；Tomcat 的 3 个 CRITICAL 显式管理三个 embed artifact。
> 还有一个细节：漏洞库给的修复版本 `10.1.58` 在 Maven Central 上被跳过了，
> 实际最新是 `10.1.61` —— **必须以仓库实际可用版本为准，不能照抄**。
>
> 不能修的，比如我遇到的 `spring-webmvc` 两个 CRITICAL，
> 修复只落在 Spring 7 / Boot 4。这时候正确做法不是关掉扫描，而是：
> **第一**，写进 `.trivyignore` 并回答三个问题——为什么修不了、路径是否可达、
> 什么时候重评。**第二**，做可达性分析：这两个 CVE 一个影响 `XsltView`、
> 一个影响 SSE，我是纯 REST 服务，两者都不可达。**第三**，写清失效条件——
> 一旦引入视图解析或 SSE，例外立即作废。
>
> 判断标准是：**例外清单要经得起审计**。只写 `ignore CVE-xxx` 不给理由，
> 等于把门禁关掉。

### Q：如果不用 Argo Rollouts 怎么做金丝雀？

**这题很能体现广度**，因为面试官所在公司未必用 Argo：

> 三层降级方案。
>
> **最轻的**：原生双 Deployment 加一个 Service，靠调整两边副本数近似分流，
> 回滚就是 `kubectl rollout undo`。缺点是比例不精确，
> 且没有自动分析——判断和回滚都要人来做。
>
> **中间的**：Nginx Ingress 的 canary annotation，能按 header 或权重分流，
> 但同样没有自动判定。
>
> **完整的**：Argo Rollouts 或 Flagger。Flagger 的特点是它把
> 「分析 + 放量 + 回滚」做成一个闭环控制器，配合 Service Mesh 做精确控流。
>
> 我的判断是：**如果团队没有专人维护发布流程，宁可用原生方案加人工确认，
> 也不要用一个没人真正理解的自动化系统**——后者在出问题时会让故障排查更难。

## 四、反问面试官

面试是双向的。下面这些问题能同时帮你判断团队成熟度，也显得你懂行：

**关于交付流程**
- 你们现在的部署频率大概是什么量级？从提交到上线要多久？
- 上一次生产事故是什么？从发现到恢复花了多长时间？
- 回滚是自动的还是人工触发的？平均多久能回滚完？

**关于技术栈**
- K8s 是自己维护还是用托管服务？集群规模多大？
- 有没有做 GitOps（ArgoCD/Flux）？还是 CI 直接 kubectl apply？
- 监控告警体系是什么？告警噪音大不大？

**关于合规（银行必问）**
- 变更需要走什么审批流程？审批在哪个环节卡点？
- 生产环境的访问权限怎么管？有没有做职责分离？
- 镜像和依赖的漏洞扫描是强制的吗？发现高危漏洞的处理时效要求是多少？

**关于团队**
- 团队里 DevOps 和开发的边界在哪？有没有平台工程的角色？
- on-call 是怎么轮值的？

**为什么问这些**：`上一次事故是什么、多久恢复的` 这个问题几乎无法准备假答案，
而且能直接反映团队的 MTTR 水平和复盘文化。

## 五、三个必须避免的坑

**不要罗列工具名。** 「我会 Jenkins、GitLab CI、ArgoCD、Prometheus、Grafana、ELK……」
这是最容易被追问穿的形式。说清楚**一个**工具解决了**什么具体问题**，比列十个强。

**不要把 demo 说成生产系统。** 面试官问「你们生产也用单副本 PostgreSQL 吗」，
硬撑会立刻暴露。正确答法是「这是我 demo 的选择，生产我会用托管数据库，
原因是……」。**知道工具的边界比会用工具更值钱。**

**不要回避不知道的。** 被问到没做过的（比如 Service Mesh、多云容灾），
说「这块我没实际做过，我的理解是……，但不确定细节」远好过编。
面试官通常能分辨，而诚实是可以加分的。

## 六、附：把仓库变成谈资

面试前做三件事：

1. **确认 CI 是绿的。** 打开 Actions 页面截图备用。
2. **跑一次 CD 的 `canary-rollback` 场景**，把 Job Summary 里那段
   AnalysisRun 失败的日志存下来。这是最有说服力的一页材料。
3. **记住三个数字**：镜像从多少降到多少、覆盖率是多少、金丝雀分析判定窗口多长。
   具体的数字比形容词可信得多。
