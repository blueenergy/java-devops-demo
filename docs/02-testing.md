# 02 测试策略：金字塔、分层、与门禁怎么定

> 一句话结论：测试的价值不在于「数量多」，而在于**每一层的失败都能指出该找谁**。
> 单测失败找逻辑，切片失败找契约，集成失败找环境——如果一层挂了你也说不出该怀疑什么，
> 这层就该重新设计。

## 一、三层结构

```
            ┌─────────────────────────────────────────┐
            │  OrderApiIT（10 个）                     │
            │  @SpringBootTest + Testcontainers       │
            │  真 HTTP + 真 PostgreSQL + 真 Flyway     │
            │  回答：这套东西组装起来能不能跑          │
            ├─────────────────────────────────────────┤
            │  OrderControllerTest（13 个）            │
            │  @WebMvcTest + @MockitoBean             │
            │  只加载 Web 层，库与连接池一概不碰        │
            │  回答：HTTP 契约对不对（状态码/结构/校验）│
            ├─────────────────────────────────────────┤
            │  OrderServiceTest + OrderTest 等（59 个）│
            │  纯 Mockito，毫秒级                       │
            │  回答：业务规则对不对（状态机/边界/副作用）│
            └─────────────────────────────────────────┘
```

| 层 | 数量 | 单次耗时 | 失败时先怀疑 | 不怀疑 |
|---|---|---|---|---|
| 单元测试 | 59 | <1s | 业务逻辑本身 | 环境、配置 |
| 切片测试 | 13 | ~5s | 路由、校验、异常映射 | 数据库 |
| 集成测试 | 10 | ~15s | 迁移脚本、真实 SQL、装配 | 单元逻辑（已被下层排除） |

**分工原则**：同一件事只在一层验证。真实 SQL 行为由集成测试覆盖后，
服务层单测就 mock 掉仓储；HTTP 契约由切片测试覆盖后，集成测试就不再重复断言校验错误。
重复测试不只浪费时间，它们**会在重构时同步变红**，让你分不清哪一层先坏。

## 二、集成测试为什么必须用真实数据库

这是本仓库最坚定的一个决策。H2 的常见辩护是「快」，但它的四个差异让「通过」失去意义：

| 差异 | 后果 |
|---|---|
| SQL 方言 | 迁移脚本里的 `TIMESTAMPTZ`、`GENERATED ... AS IDENTITY` 在 H2 上语义不同甚至报错 |
| 约束行为 | H2 默认不强制外键（PG 强制），CHECK 约束的历史行为也曾静默忽略 |
| 事务隔离 | 默认隔离级别不同，并发缺陷只在真库上暴露 |
| 类型系统 | 数组、JSON、区间类型的行为差异会导致「测试过了、生产错了」 |

Testcontainers 的代价是每个测试类 2-4 秒的容器启动（本机，镜像已缓存），
换来的是「**集成测试通过 = 生产也能跑**」这个结论成立。这个交换很值。

`@ServiceConnection`（Boot 3.1+）省掉了 `@DynamicPropertySource` 样板：
Spring 识别出容器类型后自动装配 DataSource，连 JDBC URL 都不用拼。

**注意**：Testcontainers 锁在 1.21.4 不升 2.x——Boot 3.5.16 的 BOM 管理的
就是 1.21.4，`@ServiceConnection` 的集成按 1.x 写的，跨大版本升级会踩坑。

## 三、切片测试的两个坑（都真实踩过）

### 坑 1：配置类未注册 → 上下文整体失败，报错指向别人

`FaultInjectionFilter` 是 `Filter` bean，会被 `@WebMvcTest` 切片加载；
它依赖的 `FaultInjectionProperties` 用 `@ConfigurationPropertiesScan` 注册，
而切片通过 `TypeExcludeFilter` 把不属于本切片的配置类排除掉了。
症状是 `No qualifying bean of type 'FaultInjectionProperties'`，
表现为整个上下文启动失败、**所有**测试一起报错。

修复：启动类改用 `@EnableConfigurationProperties` 显式注册。配套地，
切片里还缺 `MeterRegistry`（指标自动配置不属于 Web 切片），
由 `@TestConfiguration` 补充一个 `SimpleMeterRegistry`。

### 坑 2：`@Nested` + `@MockitoBean` 的 stubbing 跨方法泄漏

两者的 reset 生命周期对不上，上一个测试注册的 `thenThrow` 泄漏到下一个测试。
而 `when(mock.method())` 这个写法**会先真实调用一次方法**，
于是 `when(...)` 还没执行完就抛异常，栈顶指向一行看起来毫无问题的 stubbing 代码。
扁平化测试类走标准生命周期后问题消失——分组带来的可读性不值得换这种不确定性。

## 四、覆盖率门禁怎么定

三个数字的来源与理由：

```
全局行覆盖率 ≥ 80%     —— 低于此值说明存在大片的未验证路径
全局分支覆盖率 ≥ 70%   —— 分支比行难覆盖，要求放低但不放空
单模块行覆盖率 ≥ 60%   —— 防止高覆盖模块掩盖零覆盖模块
```

**认识**：门禁的目的不是追求 100%。100% 的代价是给 getter/DTO 写无意义的
测试来凑数，这些测试在重构时只会制造噪音。门禁的目的是**防止回归趋势**：
覆盖率从 92% 掉到 81% 没人会发现，但掉穿 80% 流水线会红。

实现上有个必须知道的坑：**`jacoco:check` 只读本模块的 `jacoco.exec`，没有聚合能力**。
把 check 绑到每个模块上，`demo-common`（纯 DTO）永远达不到阈值，构建必然红。
正确做法：各模块只采集，判定的脚本在 CI 层读聚合报告（见 `scripts/check-coverage.py`）。

## 五、测试的命名与断言习惯

- `@DisplayName` 写**行为与结果**而不是方法名复述：
  `取消已成交的订单被拒绝` 优于 `testCancelFilledOrder`。
- 断言用 AssertJ 的可读链（`assertThat(x).isNotNull().hasSize(3)`），
  且**带业务含义的失败信息**。断言失败的那一刻，日志应该已经告诉你答案。
- 概率性行为用确定性参数测：故障注入测试固定 1.0/0.0 而不是 0.5，
  概率断言是测试套件里最讨厌的不稳定因素。
